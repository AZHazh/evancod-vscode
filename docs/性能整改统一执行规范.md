# Evancod 性能问题整改执行计划

> 本文的目标不是“让日志变少”或“尽快停止任务”，而是在保持任务完整性的前提下找出并消除真正的性能瓶颈。

## 1. 问题与目标

当前问题：扩展启动卡顿、模型列表获取慢、授权工具响应慢、Query 执行时 VS Code 无法正常使用。

已知日志基线：Provider 3722ms、MCP 2197ms、Skill 2875ms、启动 RSS 610MB；Query 116394ms，最慢模型请求 54610ms，最大事件循环延迟 4987ms，Query RSS 1941MB，Heap 1399MB。

整改目标：

- 区分网络请求、工具执行、JSON 序列化、持久化、Webview 通信和事件循环阻塞的耗时；
- 启动 P95 小于 5 秒，启动阶段事件循环延迟小于 200ms；
- Query 阶段事件循环延迟通常小于 500ms，内存不持续增长到 1.2GB 以上；
- New API 授权只在用户点击后轮询，授权结束立即停止；
- 对标 Codex 和 Claude Code，长任务必须完整执行，不能把未完成任务显示为成功。

## 2. 不可违反的正确性约束

1. 不得把 `MAX_ITERATIONS = 100` 简单改成 20 或 30。100 是防止复杂任务被提前中断的保护值，不能作为正常完成条件。
2. Query 只有在模型明确完成且无待处理工具调用、用户取消、权限拒绝已回灌、Provider/工具不可恢复错误，或确认重复无进展并完成一次无工具收尾请求时才能结束。
3. 单次请求慢、轮数多、内存短时升高，都不能单独触发取消。
4. 不能静默截断文件、丢弃工具结果、错配工具调用，或删除错误/权限/取消逻辑来换取性能。
5. 分段读取和并发限流只能限制单次资源占用，不能限制任务总工具调用次数。
6. 任务非正常结束时，界面必须显示已完成步骤、未完成步骤、终止原因和继续方式；日志必须写入 `completed: false`。

## 3. 后续大模型的执行流程

每次继续本计划时严格执行：

1. 读取本文全文，执行 `git status`，保留用户已有修改，不重置或回滚。
2. 阅读当前阶段涉及的调用链、类型定义和测试，确认问题后再编辑。
3. 一次只实施一个阶段。每阶段完成后运行 `npm run compile` 和对应回归测试，再决定是否进入下一阶段。
4. 保留并扩展性能日志。日志只记录耗时、数量、字节数、状态和原因，不记录 API Key、Token、Authorization Header、完整消息、文件内容或完整模型响应。
5. 每次报告必须列出修改文件、验证命令及结果、日志路径、关键指标前后对比和未解决风险。没有测量结果的目标必须标为“未验证”。

## 4. 分阶段实施计划

### 阶段一：控制单次资源规模

涉及：`src/core/tools/file/FileReadTool.ts`、`src/core/tools/execution/ToolExecutor.ts`、`src/core/tools/execution/ToolOrchestrator.ts`。

执行内容：

- `read_file` 默认单次最多返回 32KB；支持 `offset`、`limit` 或行范围继续读取；截断结果必须返回文件总大小、已返回范围和下一步读取参数。
- 并发安全工具默认最多 4 个，超出后排队；记录排队耗时和执行耗时；结果按调用顺序回灌。
- 任何限制都不能阻止模型继续发起后续分段读取或其他工具调用。

验收：大文件可完整分段处理；多个文件读取不会造成数百 MB 瞬时增长；工具调用和结果严格一一对应。

### 阶段二：消除重复大对象

涉及：`src/core/engine/QueryEngine.ts`、`src/services/chat/ChatService.ts`、`src/services/chat/SessionPersistenceService.ts`、`src/services/webview/WebviewManager.ts`。

执行内容：

- 每轮请求记录消息数量、文本字节数、工具结果数量/字节数、图片数量、构建耗时、JSON 序列化耗时和序列化大小。
- 不在 `messages`、`transcript`、Webview 状态中重复保存完整文件内容；transcript 保存摘要和引用，模型上下文保留完成任务所需内容。
- 图片和 Base64 不作为普通文本重复回灌；content delta 不触发全量持久化；增量事件使用稳定索引或 Map，避免大型 transcript 线性扫描。

验收：连续读取文件后 RSS 不线性增长；Heap 通常低于 500MB；Query RSS 通常低于 800MB且不持续超过 1.2GB；会话恢复内容正确。

### 阶段三：消除 Extension Host 阻塞

全仓库检查并处理 `readFileSync`、`writeFileSync`、`statSync`、`existsSync`、`readdirSync`、`execSync`、`spawnSync`，重点检查图片、文件搜索、文件读取和 Bash 工具。

执行内容：使用 `fs.promises` 或 `vscode.workspace.fs`；大文件先检查大小；Query、权限、Webview 回调禁止同步 IO；Webview 高频消息按 32至50ms 合并；单条消息超过 64KB 时记录并拆分或摘要。

验收：`eventLoop.lag` 通常小于 500ms，不再频繁出现 1至5 秒阻塞，VS Code 主界面保持可操作。

### 阶段四：启动、MCP 和网络流程

涉及：`src/extension.ts`、Provider/Skill/Memory 初始化代码、`src/services/newapi/NewApiSyncService.ts`。

执行内容：无依赖初始化有限并行；MCP 后台连接且有超时；启动只加载当前会话；大文件和图片延迟加载；模型列表短时缓存。

New API 流程必须是：用户点击授权/同步 -> `startSync()` -> 打开授权页 -> `pollAuthorization()` -> 成功/失败/取消/超时 -> `exchangeCode()` -> 清理定时器和请求。启动时不得调用轮询；重复点击取消旧轮询；关闭 Webview、停用扩展和用户取消都要中止请求。

## 5. 必须写入的性能日志

日志路径：当前工作区 `.evancod/performance.log`；无工作区时使用系统临时目录中的 `evancod-performance.log`。

至少包含：

```text
startup.*
newapi.authorization.*
newapi.exchange.*
query.start
query.iteration.*
query.api.*
query.tools.*
tool.*
permission.*
persistence.*
webview.performance.*
eventLoop.lag
query.termination
```

每条 Query 终止日志必须包含 `terminationReason`、`iteration`、`completed`、`progressSignals`、`noProgressTurns`。稳定终止原因使用：`completed`、`user_cancelled`、`permission_denied`、`provider_error`、`tool_error`、`repeated_no_progress`、`aborted_by_extension`。`max_iterations` 只能是异常保护字段，不能代表成功。

## 6. 固定回归测试

每阶段至少验证：空工作区启动、含大量 Skill 启动、MCP 不可用启动、简单 Query、小文件读取、多个文件并行读取、大文件分段读取、写文件并批准权限、权限拒绝、工具失败后继续、用户取消、50 轮以上长任务。

必须保存并比较：启动各阶段耗时、Query 总耗时、每轮 API 耗时、每个工具耗时、请求/结果数量和字节数、序列化/持久化耗时、Webview 消息数量和大小、RSS/Heap 峰值、最大事件循环延迟。

## 7. 阶段完成标准

每阶段报告以下项目的“通过/未通过/未验证”：任务完整性、工具结果配对、日志可定位性、RSS/Heap/eventLoop 前后对比、`npm run compile`、相关测试。任何一项未通过都不能进入下一阶段或宣称整改完成。

最终完成必须同时满足：长任务未因固定小上限截断；未完成不显示成功；授权不在启动时轮询；取消可结束；工具结果无丢失/错配；日志可明确区分各类耗时；性能指标相较基线有实测改善。
